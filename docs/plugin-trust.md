# 插件信任与失败恢复

DSH Desk 不把 GitHub 搜索结果或 npm 包名直接标记为“可信插件”。安装与升级分成检查、确认、执行、验证四步；任何检查失败都不会静默进入安装。

## 安装前检查

| 来源 | 可检查内容 | 信任边界 |
|---|---|---|
| npm registry | 包名、版本、repository、`dist.integrity`、顶层生命周期脚本 | integrity 只能证明下载内容与 registry 元数据一致，不代表维护者身份或代码安全 |
| 本地目录 | `package.json` 与顶层生命周期脚本 | 没有发布者身份验证 |
| 本地 TGZ | 限制包体后直接读取 `package/package.json`，不先解压或执行 | 没有发布者身份验证 |
| GitHub/Git URL | 来源类型 | 没有不可变 commit、签名或内容完整性时标为高风险 |
| 其他 URL/未知来源 | 来源类型 | 标为高风险，不展示为已验证 |

界面会显示生命周期脚本的名称和命令，并要求用户勾选确认。即使顶层 manifest 没有脚本，传递依赖仍可能包含安装脚本，因此“未发现”不等于“安全”。

## 权限边界

当前 DSH 插件协议没有标准化的权限清单。插件与 Harness 同进程运行，可能使用 Harness 已获准的文件、网络、命令和凭据能力。DSH Desk 因此不会伪造精确权限预览；界面明确展示这一有效权限上限。

未来只有在上游提供可机器验证的权限 manifest 后，才能把权限逐项预览和强制隔离做成发布门禁。在此之前，公开插件 catalog 必须是精选清单，不能把未知来源静默安装。

## 官方插件入口

官方组合包由当前运行中的 Harness 管理。Desk 的「前往主界面」和系统菜单「返回 Harness 主界面」只恢复并聚焦已有窗口；用户在侧栏选择「插件」。该操作不重导航、不传递启动 token，也不向 Harness 页面增加桌面 IPC 权限。此版本没有公开的插件面板深链。启用、安装确认和重启提示沿用官方页面，不属于 Desk 下述来源审查流程。

## 可信目录

目录随应用一起发布，不在运行时抓取 GitHub topic。每个条目必须包含精确包版本、适配的 Harness/Desk 版本、三平台状态、能力上限、复核日期和信任依据。`bundled` 只表示它已由固定的 Harness Web Profile 挂载；未来的 `available` 条目点击安装后仍必须进入来源检查和人工确认，目录身份不能绕过安装审查。社区目录（[plugin.dshdesk.com](https://plugin.dshdesk.com/)）只用于浏览和复制安装命令，不会在运行时写入可信目录。

当前 Desk 精选目录只列出已通过本项目组合配置检查的上游内置模块；这不代表社区缺少兼容插件。随附官方条目使用固定 Harness 版本；第三方条目锁定插件自己的精确版本，不要求与 Harness 版本号相同。宿主兼容性由当前 Harness 的安装与启动检查以及对应版本的生命周期验收确认。新增第三方条目前必须先在三平台完成 add、dump-config、update、remove 与失败回滚测试。

## 失败恢复

每次 add、update 或 remove 前保存 Profile 的声明状态。命令成功后必须再通过原版 DSH `--dump-config` 组合验证。

- 命令失败或组合配置无效：恢复 `package.json`、`pnpm-lock.yaml` 与 Profile patch，并按恢复后的锁文件重新安装依赖。
- 操作前没有 Profile：删除失败操作产生的新 Profile。
- 回滚本身失败：保持 Harness 停止，显示明确错误，不尝试带损坏 Profile 继续启动。
- `why` 是只读操作，不触发停机或备份。

这一机制覆盖插件命令失败和组合配置失败，不等同于恶意代码沙箱。生命周期脚本一旦获准执行，仍可能修改 Profile 之外的用户数据；这也是安装前必须明确确认的原因。
